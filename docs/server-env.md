# server.env: the settings of scripts/start-server.sh

`scripts/start-server.sh` starts `build/xenithium-server`. It reads `server.env` in the repo root when the file exists
(plain `KEY=value` lines, sourced by bash), and uses the defaults below for anything not set there. Arguments given to
the script are appended to the server's command line, so a flag passed by hand wins over the file.

- `SERVE_DRY_RUN=1 scripts/start-server.sh` prints the command without starting anything.
- `SERVE_PLAN=1` runs it with `--plan` instead: the load's memory plan as JSON (VRAM per card by part, the KV tokens the
  pool will hold, the hot experts of a MoE model, pinned host RAM, the host's free RAM). It opens no GPU and loads no
  model, so it also runs beside a live server. Parts the load only knows after measuring the cards are estimates
  (`"exact":false`). A launch the load would refuse (one max context of KV does not fit, another model's drafter) exits
  2 with the reason.
- `SERVE_ENV=FILE` reads FILE instead of `server.env` (relative to the repo root; a missing FILE is an error), e.g. a
  profile under `profiles/`.

`scripts/launch.sh` edits these settings interactively, shows each one's description, and launches and watches the
server ([launcher.md](launcher.md)). Its defaults come from the script and its flags from this page, so a setting added
here and in the script shows up there (as text until the launcher's schema in `tools/launch/settings.cpp` types it).

The script refuses to start when a xenithium-server is already running, when the port is in use, or (for the GPU
engine) when any Docker container is running: the cards must be free.

In the tables below, a **Gives:** line names what a value improves and a **Takes:** line what it costs (speed, VRAM,
the KV pool, host RAM, exactness of the output). Speeds depend on the machine and the traffic: measure yours with
`xenithium-bench` ([bench.md](bench.md)).

For the separate, default-off trained Swift indexer environment variables and compatibility rules, see
[trained K8V4 QSA](trained-k8v4-qsa.md).

## Per-model settings files

Each served checkpoint keeps its own settings in a file named `<id>.env`. A file names its checkpoint with `XEN_MODEL`.
There are two places for it:

- `models/presets/<id>.env`: the **presets** shipped with the project (tracked in git): `qwen38-flash-next.env`,
  `qwen38-w4a16-intel.env`, `qwen38-27b.env`, `qwen38-27b-intel.env`, `swift15-27b-int4-baked-qsa.env` (trained QSA; needs the selector bank),
  `flint-int4.env`, `nanbeige43-33b.env`. Nothing
  on your machine writes them; an update of the project may change them.
- `models/<id>.env`: **your own file** (git ignores everything in `models/` but `presets/`). The launcher creates it on
  the first save, starting from the preset's lines, and edits only this file from then on. You can also create or edit
  it by hand.

Your file replaces the preset of the same name, so `git pull` never changes the settings you run with. Delete your file
to go back to the preset. `server.env` only says which one to start:

    XEN_MODEL_ENV=qwen38-flash-next     # models/qwen38-flash-next.env, else models/presets/qwen38-flash-next.env

The order, last wins: the defaults below, then the per-model file, then the settings file (`server.env` / `SERVE_ENV`)
and the caller's environment - a key either of those sets wins over the per-model file, so
`XEN_PREFILL_CHUNK=512 scripts/start-server.sh` tries one change without editing anything. `XEN_MODEL_ENV`:

- an id or a path: that file (your file when it exists, else the preset of that name). It is applied only when it
  belongs to the model being started: a settings file or environment whose `XEN_MODEL` names another checkpoint falls
  back to that checkpoint's own file (auto);
- unset or `auto`: the file whose `XEN_MODEL` is the checkpoint started (`XEN_MODEL`, else the default), looked up in
  `models/` and then in `models/presets/`;
- empty: none (the defaults plus the settings file only; the launcher's `build/launch/launch.env` carries every value
  and sets it empty).

The caller's `XEN_MODEL_ENV` wins over the settings file's (`XEN_MODEL_ENV=flint-int4 scripts/start-server.sh`). The
script prints `start-server: per-model settings from <file>` when it applies one. Benchmark scripts that must run the
bare defaults pass `XEN_MODEL_ENV=` with their own `SERVE_ENV`.

The launcher edits these files: opening `server.env` opens the current model's file, a model switch (`m`) opens the new
model's file (its preset, or the defaults when it has neither), and a save writes your file `models/<id>.env` and points
`server.env` at it ([launcher.md](launcher.md)). The Settings frame's title shows `(preset)` while the values come from
a preset and `(new)` when the model has no file yet. Settings an older `server.env` still holds win until the next save
moves them into the model's file.

`server.env`, `server.env.*`, `profiles/` and `.env` are git-ignored as well: no file you edit is tracked.

## Per-setup settings files

A model that runs on more than one card count keeps each setup's settings in its own file beside the model's:
`<id>.tp<N>.env`, where N is the setup's card count. Presets: `qwen38-w4a16-intel.tp1.env` / `.tp2.env` / `.tp4.env`,
`qwen38-flash-next.tp1.env` / `.tp2.env` / `.tp4.env`, `qwen38-27b-intel.tp1.env` / `.tp2.env`, `qwen38-27b.tp1.env`, `swift15-27b-int4-baked-qsa.tp2.env`,
`flint-int4.tp1.env` and `nanbeige43-33b.tp1.env` in `models/presets/`.

The presets' slots and prefill chunk: 16 slots on two and four cards (8 on Flint and Nanbeige, their most), 4 on one
card; prefill chunks of 4,096 tokens on Qwen3.8-Flash-Next and Flint, 2,048 on Qwen3.8-27B and Nanbeige. As for the
model's file, your own `models/<id>.tp<N>.env` replaces the preset of the same name and is the only one written.

- The setup key picks the file: `XEN_Q38_TP` for qwen38, `XEN_TP` for qwen35 / llama / flint. Its value comes from the
  environment, then the settings file, then the model's file, else `2`.
- The model's file holds what all setups share: the "Model & network" settings (`XEN_MODEL`, `XEN_SERVED_NAME`,
  `XEN_HOST`, `XEN_PORT`, ...) and the setup key itself, the setup to start.
- The setup's file holds everything else for that card count (slots, KV pool, drafter, CPU path, prefill chunk, ...).
  It never names the checkpoint: the script ignores `XEN_MODEL`, `XEN_SERVED_NAME`, `XEN_MODELS_DIR` and the setup key
  in it, and the model lookup skips these files.

The order, last wins: the defaults, the model's file, the setup's file, then the settings file and the caller's
environment. So `XEN_Q38_TP=4 scripts/start-server.sh` starts the TP4 setup with its own settings. The script prints
`start-server: per-setup settings from <file>` when it applies one. A setup without a file runs the model's file and
the defaults.

In the launcher, changing the setup key (Cards) loads that setup's file; with unsaved changes to the current setup it
asks first. `s` writes the shared settings to your model file and the rest to your setup file. The setup's file only
gets what differs from the model's file and the defaults; keys it already lists stay as written, comments too.

## MoE expert files: the hot-expert ranking

A MoE model (qwen38) may hold only part of its routed experts in VRAM; the rest stay in pinned host memory and are read
over PCIe when a token routes to them. Which experts are hot decides how often that happens. One file per model feeds
it, `.cache/experts/<model folder>/hot-rank.xrc` of the repo (the `auto` value of `XEN_HOT_RANK`; git-ignored, so a
re-clone starts without it: copy the folder over to keep it):

| file | setting | written by | read | archs |
| --- | --- | --- | --- | --- |
| `hot-rank.xrc` (the ranking) | `XEN_HOT_RANK` | the server while it serves (every 60 s of decoding and at exit); optionally `scripts/make-hot-rank.sh` | at boot | qwen38 |

- The ranking is learned: the server counts which experts the decode steps read and keeps a long-term score per expert
  (half-life 60 minutes of decode traffic); the next boot puts the best-scored experts in VRAM. The first run of a model
  starts from the default placement (an even split) and creates the file after its first minute of decoding. Delete the
  file to start over. The hot set stays as placed at boot until the next start.
- Optional: `scripts/make-hot-rank.sh` replaces the file with the counts of a calibration run on 40 sample chats (a
  start before any traffic; the server then keeps recording on top of it).
- `scripts/make-hot-rank.sh [--model DIR] [--out F] [--prompts F.jsonl] [--gen N]` needs `build/xenithium-probe` and
  the cards free (no server, probe or container), and takes the model's load time plus 1-3 minutes of decoding.

## Cards: detection and emulation

The engine runs on the Battlemage cards of its table (`include/xenithium/util/cards.hpp`): Arc Pro B70 (BMG-G31, PCI id
`e223`, 32 Xe cores, 32 GB, 608 GB/s, 2,800 MHz), Arc Pro B65 (BMG-G31, `e222`, 20 Xe cores, 32 GB, 608 GB/s,
2,400 MHz) and Arc Pro B60 (BMG-G21, `e211`, 20 Xe cores, 24 GB, 456 GB/s, 2,400 MHz). One binary serves all three: the
device code is compiled for `bmg` (IP 20.1.0, the G21 die), which the G31 cards run.

At start every server, probe and test names each card it opens, once per process:

```
card 0: Arc Pro B70 (BMG-G31, by pci id): 32 Xe cores, 30.3 GiB, 608 GB/s, 2,800 MHz; Intel(R) Arc(TM) Pro B70 Graphics at 0000:03:00.0
```

A card is identified by its PCI id, then by the driver's name ("Pro B60"), then (an unlisted Battlemage id) by its Xe
cores and memory; a card outside the table is named `unknown card` and runs on its own measured cores and memory. What
the engine reads from the identified card: the Xe core count sizes the kernels' waves (`rt::xe_cores`: the attention
tail plan, the W4 decode GEMM's thread slots, the W4A8 prefill's tile choice), the free memory
(sysman) sizes every budget, and `--plan` (no device opened) budgets for the first card in sysfs.

`XEN_EMU_CARD=b60|b65` runs as that card on a bigger one (a B70; a B60 also on a B65; a larger card is refused):

| part | emulated | how |
| --- | --- | --- |
| identity | yes | the `card N: emulating ...` line |
| Xe core count the kernels plan for | yes | `rt::xe_cores` returns the emulated card's cores |
| VRAM | yes (B60: 8 GiB less) | sysman's size and free memory (`l0::vram_state`) and `Device::budget_vram` hide the difference, so the KV pool, hot experts and every budget size themselves for 24 GB |
| cores taken away | no | the B70's other 12 cores still run work-groups: compute-bound speed is still the B70's. The driver offers one compute engine: a kernel that holds cores from another queue, process or the render engine is time-sliced with the engine's kernels instead of sharing the card, so no software way exists |
| bandwidth (B60 456 GB/s) | no | memory-bound speed is still the B70's (same reason); scale decode by 608 / 456 = 1.33x |
| clock (2,400 vs 2,800 MHz) | no | needs root (`xpu-smi config --frequencyrange`) |
| L2 size, PCIe link | no | |

So an emulated run is exact for memory budgets, context and hot-expert fits and for the launch-shape code paths, and its
speed is a B70's: for B60 / B65 speed, scale by arithmetic (memory-bound parts by the bandwidth, DPAS-bound parts by
20 x 2,400 / (32 x 2,800) = 0.54) or measure on the real card.

## Switches the server reads itself

The settings in this section and the next two are read from the environment by the server itself (not by
`start-server.sh`, not in `server.env`'s defaults); `start-server.sh` passes on whatever a settings file or the shell
sets. A switch is on only when set to a non-empty value other than `0`: unset, empty and `0` are all off (the trained
page selection's switches: on only with the value `1`).

| variable | meaning |
| --- | --- |
| `XEN_PREFILL_SHARE` | How the loop divides its time between reading new prompts and generating for the requests that are already answering. By default every loop turn runs one prompt call (or one part of a split call) next to the generation step, so a long prompt arriving slows down every stream that is generating while it is read. With a share `s` between 0 and 1, while any request generates, prompt reading gets about `s` of the loop's wall time and generation the rest; with nothing generating, prompts run at full speed again.<br><br>`empty`  off: one prompt call or part every loop turn (the default)<br>`0.33`  about a third of the time for prompts, two thirds for generation<br><br>Gives: + steadier and faster generation for the users already answering while long prompts arrive (interactive serving with several users).<br>Takes: - a long prompt can take longer to read while others generate (it gets at most its share).<br>Note: every model. 0 and 1 also mean off.<br>Output: the same. |

## Trained page selection (Qwen3.8-27B)

Trained page selection makes long-context decoding read only part of the past. A small trained scorer per
global-attention layer (the bank, downloaded separately) ranks the context's completed four-token blocks for every
new token, and attention reads the 512 best instead of the whole context. It runs in speculative decoding past
8,192 tokens of context; prompts read the full context unless the selected prompt reading is on. It works on the
Qwen3.8-27B with the int8-v4 KV cache and a block drafter, and its replies differ from full attention. The preset
`swift15-27b-int4-baked-qsa` (start it by name: `XEN_MODEL_ENV=swift15-27b-int4-baked-qsa`) sets the recommended
switches; [trained-k8v4-qsa.md](trained-k8v4-qsa.md) has the details and measurements.

| variable | meaning |
| --- | --- |
| `XEN_TRAINED_QSA_DELTA_DIR` | Turns trained page selection on for the Qwen3.8-27B: the folder of the trained indexer, a small scorer per global-attention layer (downloaded separately; the int4-baked QSA preset names it). | `XEN_TRAINED_QSA_PREFILL_MERGED` | Gives each prompt of a merged prompt call (several prompts read in one call) its own selection, instead of reading the full prefix for all of them.<br><br>`1`  merged calls select per prompt<br>`0`  merged calls read the full prefix (the default)<br><br>Gives (1): + prompt reading speed when several long prompts arrive together.<br>Needs: XEN_TRAINED_QSA_PREFILL_4SLOT_SINGLE_SEG 1; the server refuses it otherwise.<br>Output: differs from full attention. |
| `XEN_PF_SUBTILE_SKIP` | In the selected prompt reading, skips the parts of each 40-row attention group that picked nothing from a page, instead of computing them and masking the result.<br><br>`1`  skip them<br>`0`  compute and mask (the default)<br><br>Gives (1): + prompt reading speed.<br>Takes (1): - a small table in VRAM.<br>Needs: XEN_TRAINED_QSA_PREFILL_XMX 1 with the native 40-row groups.<br>Output: the same. |
| `XEN_TRAINED_QSA_SHARE_SCRATCH` | The selector's work buffers (projections, scores, candidates) each have their own VRAM by default. This lays them over one another, sized for the largest stage at a time.<br><br>`1`  one shared buffer<br>`0`  separate buffers (the default)<br><br>Gives (1): + VRAM headroom (room for a larger KV pool or another slot).<br>Takes (1): nothing.<br>Output: the same. |
| `XEN_TRAINED_QSA_STREAM_PROJECTION` | Keeps the scorer's projection weights (three matrices per trained layer) in pinned host memory and copies a layer's matrices to the card when that layer runs, instead of holding all of them on every card.<br><br>`1`  copy from the host as needed<br>`0`  all weights in VRAM (the default)<br><br>Gives (1): + VRAM headroom: the weights of every trained layer but one.<br>Takes (1): - decode and prompt speed (a host-to-card copy for each trained layer of every step); - pinned host RAM.<br>Output: the same. |

## Diagnostic switches

Read by the server itself like the switches above. Leave them unset in production: most slow the server down.

| variable | meaning |
| --- | --- |
| `XEN_PF_LOG` | Diagnostic: one log line per prompt-processing call, part and generation step. |
| `XEN_PF_PROFILE` | qwen38 diagnostic: times every prompt-processing phase.<br><br>`1`  host time<br>`2`  device time with barriers<br>`3`  GPU clock stamps<br><br>Takes: - prompt reading speed. Never use it to measure speed. |
| `XEN_DEC_PROFILE` | qwen38 diagnostic: GPU clock stamps around every module of the generation step. The log gets one line of times per module every 512 steps.<br><br>Takes: - decode speed. Never use it to measure speed. |
| `XEN_STEP_GRAPHS` | qwen35 (Qwen3.8-27B): replay the decode step as a recorded GPU graph (with `XEN_GRAPHS` on; flint always does). Off by default.<br><br>Gives: + decode speed when the CPU is the bottleneck: a step's ~2,000 kernel launches cost one replay. Measured with the server held to a quarter of one EPYC 7532 core: 98 / 177 / 251 -> 165 / 283 / 378 tok/s at 1 / 2 / 4 streams. On a fast host: the same as without.<br>Takes: - ~42 ms the first time each step shape runs (recorded once), - about 7.5 MiB per step graph per card (`XEN_STEP_GRAPHS_MAX`); the drafter's cap (`XEN_DRAFT_GRAPHS`) drops to 72 so the total stays the same.<br>Output: the same greedy text as without, measured up to 228K-token prompts (two documents in one request). With a trained bank (XEN_TRAINED_QSA_DELTA_DIR) and the adaptive depth on, the replays time differently, so the depth picks other step shapes at some steps, and the trained selection follows the shape: the text then differs from a run without graphs, repeatably (with XEN_ADAPTIVE_DEPTH 0 it is the same).<br>Not used with page-selected attention (XEN_ATTN_SELECT above 0) or while XEN_QSA_SCORE_CHECK or XEN_QSA_PACK_CHECK is set: those steps run without graphs. |
| `XEN_STEP_GRAPHS_MAX` | The most qwen35 step graphs kept (default `32`, at least 4); the least recently replayed is dropped at the cap. |
| `XEN_GRAPH_ROOM_MIB` | qwen35 step graphs: below this much free VRAM on the tighter card (default `128`), each new step graph first drops 4 old ones. A recording that fails drops all of them and runs that step without a graph. |
| `XEN_DRAFT_GRAPHS` | Block drafter (DFlash 2 / DSpine): the most recorded drafter-pass graphs kept on the cards (a number, at least 4; default `96`, `72` with `XEN_STEP_GRAPHS`). Each holds about 10 MiB per card; once the cap is reached the least recently used one is dropped, and the log says so once.<br><br>Lower: + VRAM headroom on tight cards. Takes: - a recording (~20-40 ms) whenever a dropped step shape comes back.<br>Output: the same. |
| `XEN_QSA_PF_TILES` | qwen38 numerics switch for the prompt's attention.<br><br>`empty`  the faster 8-tile prompt attention (the default)<br>`1`  the generation step's tiling: bit-equal to it<br><br>Gives (1): + bit-equality of prompt reading with generation.<br>Takes (1): - a little prompt reading speed. |
| `XEN_REQ_LOG` | Diagnostic: one `REQ_DONE` log line per finished request with its slot, prompt and cached tokens, tokens generated, time to first token, decode time and speed, verifier steps and tokens per step, the average number of streams beside it, and why it finished.<br><br>Takes: nothing measurable (one line per request). |
| `XEN_DEPTH_TRACE` | Diagnostic for the adaptive draft depth (XEN_ADAPTIVE_DEPTH): a log line each time it changes the depth or the drafter layers used at a stream count, with the tokens per millisecond before and after.<br><br>Takes: nothing measurable. |
| `XEN_QSA_TRIAL_ROUTE_LOG` | Trained page selection diagnostic: one log line per stream per verifier step with the route its attention took and why: `covered` or `covered-tree` (selected), `short` (under the threshold), `incomplete` (history missing, e.g. resumed from the cache), `tree` (tree steps without XEN_TRAINED_QSA_TREE), `mixed`.<br><br>Takes: - decode speed (very verbose). Never use it to measure speed. |
| `XEN_QSA_PACK_CHECK` | Trained page selection diagnostic: for the first N steps on card 0, reads back the packed attention entries and checks them against a host reference; the log reports mismatches.<br><br>`0`  off (the default)<br><br>Takes: - decode speed during the checked steps (waits on the card). |
| `XEN_QSA_SCORE_CHECK` | Trained page selection diagnostic: for the first N XMX scoring passes on card 0, also computes the scores with the vector scorer and logs how far the two differ.<br><br>`0`  off (the default)<br><br>Needs: XEN_QSA_XMX_SCORE 1 and XEN_TRAINED_QSA_POOL_FP16 1.<br>Takes: - decode speed during the checked steps. |
| `XEN_PF_DENSE_ONEDNN_LOG` | qwen38 diagnostic for the oneDNN prompt GEMMs of the dense trunk (XEN_PREFILL_GEMM onednn): one line per new matrix shape saying whether oneDNN or the engine's own kernel runs it (oneDNN is kept only where it gives the engine's bits). |
| `XEN_PF_DENSE_ONEDNN_SLOTS` | qwen38, oneDNN prompt GEMMs of the dense trunk: how many repacked weight matrices stay cached on each card.<br><br>`empty`  4 (the default)<br><br>More: + fewer repacks during long prompts; - VRAM (one largest int8 matrix per slot). |
| `XEN_PF_ONEDNN_SLOTS` | The int4 prompt GEMMs on oneDNN (XEN_PREFILL_GEMM onednn): how many repacked int4 weight matrices stay cached on each card.<br><br>`empty`  2 (the default)<br><br>More: + fewer repacks per prompt call; - VRAM (one repacked matrix per slot). |

Request-level features need no setting: structured output (`response_format` json_object /
json_schema, `guided_json`, `guided_choice`, `structured_outputs` json / choice, `tool_choice`
required / named) and prompt logprobs (`prompt_logprobs`, echo + logprobs) are on.
`guided_regex` / `guided_grammar` answer 400.
